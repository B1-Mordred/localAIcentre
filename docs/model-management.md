# Model Management

Models are represented by immutable manifests and content-addressed blobs. The authoritative model tree lives outside Git under `$B1_DATA_ROOT/models`.

Required lifecycle:

1. Resolve a manifest from an approved catalog, direct URL, or upload.
2. Validate source URL policy and licence.
3. Stage downloads in a partial area.
4. Verify size and SHA-256.
5. Publish atomically.
6. Create runtime-specific read-only views.
7. Run optional smoke inference and record measured RAM/VRAM.
8. Quarantine before permanent removal.

Initial alias seed data is in `model-catalog/seed/aliases.json`. Seed manifests live beside it as `*.manifest.json` files and are mounted read-only into the control plane at `/opt/b1/model-catalog`.
Initial target-class profiles are in `model-catalog/seed/model-profiles.json` and are validated against the alias seed and known catalog manifests. Profiles describe the intended alias group, modality, runtime class, RTX 3060/32 GB resource estimate, default safety limits, and operator selection guidance without naming untested rapidly changing GPU models. The Control Center shows these required profiles next to aliases and in a dedicated table so administrators can bind exact pinned manifests later while keeping public client aliases stable.

Current scaffold behaviour:

- `GET /v1/models` returns enabled public aliases visible to the caller with status, modality, preferred runtime, resource label, and whether it is a CPU-resident candidate. Installed PostgreSQL model records overlay the seed catalog and can activate previously uninstalled aliases.
- All `/admin/models*` endpoints require an `admin` or `operator` role in addition to their `models:*` or `storage:*` scope. Lower-privilege service, creator, and user clients with `models:read` use `/v1/models` or Model Hub APIs and cannot inspect Control Center model-management state.
- `GET /admin/models` returns public alias state, required model profiles, persisted alias policies, known catalog manifests, and database model records for the Control Center.
- The Control Center Models tab shows aliases, required model profiles, and catalog recommendations separately. Aliases expose policy controls and installed-model actions, required profiles explain what class of model/workflow each alias needs, and catalog recommendations such as `b1-piper-en-us-amy-low` can be planned, downloaded, and installed directly by immutable model ID before they activate a public alias.
- `PUT /admin/models/aliases/{alias}/policy` persists operator-controlled alias policy in PostgreSQL: enabled/disabled state, preferred runtime override, idle timeout seconds, visibility roles, and notes. Disabling an alias refuses active jobs and active runtime reservations for that alias, refreshes workflow dependency readiness, and makes inference calls fail with an explicit administrator-policy error. While active runtime reservations exist, preferred-runtime and visibility-role changes are refused because they would alter alias resolution for the reserved GPU window; idle-timeout and notes-only updates remain allowed. Reservation dependency reports expose only safe public fields and omit reason text and idempotency keys. A blank idle timeout uses `B1_GPU_DEFAULT_IDLE_TIMEOUT_SECONDS`; a non-blank value overrides that default for the alias.
- `DELETE /admin/models/aliases/{alias}/policy` removes the database override and reverts the alias to the repository seed and installed manifest defaults. If active runtime reservations exist, reset is refused when it would change preferred runtime or visibility roles.
- `POST /admin/models/install-plan` validates a catalog, uploaded, or remote-URL manifest, checks source URL policy, reports licence acceptance, verifies content-addressed blobs, and evaluates the RTX 3060/32 GB resource policy before installation. The Models tab exposes the same sources: catalog buttons for known models and a Manifest URL field for approved HTTPS JSON manifests.
- Manifest operations are validated against the declared modality during catalog load and install planning. Known endpoint synonyms such as `responses`, `embeddings`, `speech`, `audio-transcriptions`, `text-to-image`, and `image-to-image` are stored as canonical operations before alias/runtime resolution, while wrong-modality or duplicate-after-normalization operation lists are rejected.
- Manifests may declare governance metadata required for long-lived Model Hub operation: `runtime_adapter_versions` maps listed runtimes to tested/compatible adapter version ranges, `companion_files` lists required or optional companion paths with optional hashes and sizes, `permissions` records role intent for visibility, installation, downloads, and inference, `deprecation` records active/deprecated/replaced/removed status plus replacement metadata, and `runtime_smoke` defines a versioned, bounded runtime-specific smoke payload. ComfyUI-backed production manifests should include `runtime_smoke.schema=b1-ai-hub-runtime-smoke/v1` and a small native API-format `runtime_smoke.comfyui.prompt` so install smoke uses ComfyUI's real validation, queue, lazy model loading, and history. The Control Center shows a redacted runtime-smoke summary with configured runtimes, probe shape, prompt-node count, and timeout, but does not render raw prompt JSON. Model Hub metadata replaces `runtime_smoke` with the same redacted summary for external clients. The catalog parser rejects unsupported runtime names, adapter versions for runtimes not listed by the manifest, unsafe companion paths, duplicate companion paths, invalid roles, malformed runtime-smoke payloads, and `replaced` records without a replacement model. Model Hub read, sync-plan, and blob routes enforce `visible_to` and `downloadable_by` for non-admin clients in addition to dedicated Model Hub client allowlists. Admin install-plan, upstream blob-staging, and install routes enforce `permissions.installable_by` for non-admin clients. Runtime alias resolution also enforces `permissions.inference_roles` for non-admin inference, job, audio/media, and reservation requests.
- Seed manifests marked `installation_status: available` are treated as operator recommendations, not placeholders. They must include a license URL, attribution, an explicit `acceptance_required` value, at least one alias, a non-upload source URL/revision, and a complete `measurements` block with `updated_at`, original/latest resource estimates, and at least one `ok` run tied to the exact `model_id@version`. This keeps initial recommendations auditable with a tested version, download source, licence context, measured hardware result, and date before they appear in the Control Center catalog.
- Required model profiles are not recommendations for a specific model release. A GPU alias can remain uninstalled while its profile still shows the target class, preferred runtime, default context/resolution/frame/batch limits, and current resource-policy label. Exact GPU manifests must be added only after pinned source, licence, hash, smoke probe, and measured RTX 3060 evidence are available.
- `POST /admin/models/download-plan` and `POST /admin/models/downloads` stage direct-url model blobs into the authoritative content-addressed store with durable aggregate status, optional encrypted bearer credentials, per-file resume, pause/resume controls, cancellation, retry/requeue after failed or cancelled attempts, size verification, SHA-256 verification, and atomic publication. The background worker recomputes the exact `$B1_DATA_ROOT/models/blobs/{sha256}` and `.partial/{sha256}.partial` paths from the target digest and refuses any stored download record or file plan whose paths do not match. Manifests declaring `license.acceptance_required=true` require `accept_license=true` before an administrator can queue blob staging; that acceptance is persisted on the download record and is rechecked by the background runner, so legacy or unaccepted records fail closed even when the blob already exists.
- `POST /admin/models/install` requires `confirm=true`, and `accept_license=true` when the manifest requires acceptance. It only publishes manifests whose blobs already exist under `$B1_DATA_ROOT/models/blobs/{sha256}` and match size and SHA-256. Before the database record is marked installed, the control plane creates runtime-specific model views under `$B1_DATA_ROOT/models/runtime-views/{runtime}/{model_id}/{version}`. Ordinary files are hardlinked into those views; archive-format files are inspected and safely extracted into the view after traversal, unsafe type, duplicate path, parent/file conflict, and archive-bomb checks pass. View creation is staged under `$B1_DATA_ROOT/models/runtime-views/.staging` and published only after every runtime view has built successfully, so a failed extraction or link does not leave a partially visible final runtime view. Setting `smoke_test=true` runs the same smoke-test path immediately after install.
- `POST /admin/models/{id}/versions/{version}/smoke-test` runs an operator-triggered runtime smoke test. GPU-backed models acquire the global scheduler lease, unload other GPU runtimes, verify the VRAM reserve, call load/warm/smoke runtime hooks, and mark the runtime idle afterward. CPU `audio-cpu` models call `/b1/runtime/smoke` without a GPU lease and report `peak_vram_mib=0`. Successful smoke runs append a bounded `measurements` block to the stored manifest and update `resource_estimate` conservatively from measured peak RAM/VRAM so admission labels can become stricter after real observations. Unsupported or failed smoke hooks are audited but do not replace the manifest estimate.
- `DELETE /admin/models/{id}/versions/{version}` requires `confirm=true`, refuses active jobs and active Voicebox voice-profile references by immutable model or alias, refuses active runtime reservations by immutable model version, reports dependent workflows, voice profiles, and scheduler reservations, moves runtime views to `$B1_DATA_ROOT/models/quarantine/runtime-views`, and marks the database record `quarantined`.
- `GET /admin/models/{id}/versions/{version}/blob-quarantine-plan` and `POST /admin/models/{id}/versions/{version}/blobs/quarantine` provide a second, explicit cleanup stage for authoritative blobs after the model record is already quarantined.
- `GET /modelhub/v1/catalog` returns both alias projections and manifest records. Administrator wildcard credentials see the full catalog; dedicated Model Hub clients see only aliases and manifests matched by their `allowed_models` policy.
- `GET /modelhub/v1/models/{id}` accepts either a public alias such as `tts-fast` or an immutable model ID such as `b1-cpu-placeholder-tts`. Model Hub model/detail/sync requests and dedicated-client `allowed_models` entries accept only safe B1 identifiers: alphanumeric first character, then ASCII letters, digits, `.`, `_`, `+`, or `-`, up to 128 characters. Unsafe values are rejected before dedicated-client lookup, catalog lookup, or catalog authorization.
- Model Hub catalog, model, version, and sync-plan responses redact manifest `source.url` values for external consumers by removing credentials, query strings, fragments, and signed-token material. Use admin model-management endpoints for the authoritative source URL.
- Inference-only manifests cannot advertise downloadable or network-share execution modes.
- `POST /modelhub/v1/sync/plan` returns licence, attribution, redacted source, execution mode, immutable model version, and resource-estimate metadata on every keep/download/replace/skip action. Official `b1-model-client` sync and daemon runs require `--accept-license` or `B1_MODEL_CLIENT_ACCEPT_LICENSES=true` before synchronising manifests whose licence requires acceptance, then send `X-B1-Accept-License: model_id@version` on gated blob requests. Model Hub blob requests accept only exact SHA-256 hex digests; malformed values are rejected by the control plane before policy lookup, rate limiting, or artifact-server proxying.
- Manifest aliases must match the modality declared in the alias seed.
- The initial placeholders for `embedding-default`, `tts-fast`, and `stt-default` are development-only CPU records. They do not bundle model weights and are not downloadable. Scaffold CPU audio/embedding responses identify themselves with `b1_placeholder=true` or `X-B1-Placeholder: true`; set `B1_CPU_AUDIO_ENABLE_PLACEHOLDER=false` to make scaffold endpoints fail with HTTP 503 and model smoke report `status=unconfigured` until a real pinned CPU runtime is configured. `B1_CPU_AUDIO_ENGINE=piper` is the first real CPU TTS adapter path: the default `audio-cpu` build installs rhasspy/piper `2023.11.14-2` at `/opt/piper/piper` with a pinned SHA-256, and the catalog includes `b1-piper-en-us-amy-low` as an available, not-yet-installed voice recommendation. `B1_CPU_EMBEDDING_ENGINE=onnx` enables the first real CPU embedding adapter path; the default image includes pinned ONNX Runtime, tokenizer, and NumPy dependencies, and the catalog includes `b1-minilm-l6-v2-onnx-q4` as an available, not-yet-installed MiniLM recommendation. `B1_CPU_STT_ENGINE=vosk` enables the first real CPU STT adapter path; the default image includes pinned Vosk Python bindings, and the catalog includes `b1-vosk-small-en-us-0.15` as an available, not-yet-installed small English recommendation. Installing any of these manifests creates the read-only `audio-cpu` runtime view, and synchronous/asynchronous requests forward the immutable resolved model version so the runtime can select the voice, embedding model, or STT model without shell edits. Piper responses identify themselves with `X-B1-Placeholder: false`; ONNX embedding responses identify themselves with `b1_embedding_engine=onnxruntime` and `b1_placeholder=false`; Vosk transcription responses identify themselves with `b1_stt_engine=vosk` and `b1_placeholder=false`. Each CPU engine satisfies only its own modality.

Seeded but uninstalled aliases remain visible so clients can bind to stable names before model installation. Runtime calls against those aliases must fail with explicit capability/dependency errors until a compatible manifest has been installed and validated.

Alias visibility roles are optional. An empty role list means any authenticated role with the required API scope may see/use the alias. When roles are set, `/v1/models` hides the alias from other roles and runtime submission returns HTTP 403 before model loading. Administrator catalog views still show all aliases so policy can be repaired from the Control Center.

The GPU runner marks a prepared runtime idle when queued GPU work or synchronous GPU-backed OpenAI-style work finishes. When no GPU job is waiting, it checks idle runtime state, applies the alias-specific timeout or the environment default, acquires the same global GPU scheduler lease, and asks runtime-agent to unload the expired runtime. Active streams, native ComfyUI prompts, reservations, or media jobs keep the lease and block idle unload until they finish.

The authoritative blob library is content-addressed under `$B1_DATA_ROOT/models/blobs/{sha256}`. Inference containers do not mount that blob library directly. LocalAI, ComfyUI, Voicebox, and CPU audio each mount only their own `$B1_DATA_ROOT/models/runtime-views/{runtime}` subtree read-only. The control plane creates hardlinks from verified blobs into those runtime views so containers can read the exact file paths declared by a manifest without listing or mutating the authoritative blob library. The artifact-server exposes blob bytes only on internal Docker networks and requires the generated internal service token, while external clients reach them through the authenticated control-plane Model Hub route with downloadable-policy checks, per-client allowlists, CIDR checks, `ETag`/`If-None-Match` support, and the `B1_MODELHUB_BLOB_REQUESTS_PER_MINUTE` blob-download rate limit. Blob delivery accepts only regular files, refuses symlinks, and re-hashes bytes before serving.

In the Compose deployment, the control plane is the only web-facing service with a writable mount for `$B1_DATA_ROOT/models/blobs`; that mount is used by the model-download worker for `.partial` staging, resume, checksum verification, and atomic publication. The worker refuses symlinked blob parent paths, symlinked or non-regular partial/target files, target or partial paths whose filename does not match the requested SHA-256, and existing target blobs that do not verify; partial writes use no-follow opens where the host supports them. The artifact-server mounts the same blob directory read-only, and GPU/CPU runtimes never mount it directly.

External machines should use `b1-model-client` rather than mounting the authoritative model tree. The client sends a local blob inventory to the Model Hub sync-plan endpoint, pins desired aliases in local state, downloads only permitted content-addressed blobs, verifies HTTP metadata and SHA-256 before publication, supports conditional revalidation through content-addressed ETags, forces POSIX cache directories/files to owner-only modes, and prunes only blobs that it previously marked as managed. This keeps external ComfyUI, Voicebox, or batch clients from depending on live network-mounted model loading and avoids deleting operator-managed local files.

The first download worker is deliberately narrow but supports multi-file HTTPS `direct-url` manifests and Hugging Face repository manifests. A single-file direct-url manifest treats `source.url` as the exact file URL. A multi-file direct-url manifest treats `source.url` as a base URL ending in `/`, appends each safe manifest `files[].path`, and rejects query strings or fragments on the base URL. Manifest paths with traversal, encoded separators, query/fragment controls, malformed percent escapes, or invalid percent-encoded UTF-8 are rejected before they can become runtime view paths or generated download URLs. Hugging Face manifests use `source.type: "huggingface"`, a repo URL under `https://huggingface.co/...`, a simple branch/tag/commit `source.revision`, and normal manifest `files[]` records with exact SHA-256 and size values; the control plane derives `/resolve/{revision}/{path}` URLs. Embedded username/password values and credential-like query parameters, including signed URL keys such as `download_token`, `X-Amz-Signature`, and `X-Goog-Credential`, remain blocked on manifest source URLs. If a target content-addressed blob already exists but does not verify, planning blocks instead of overwriting it.

Remote manifest imports use `manifest_url` on install-plan, download-plan, download-create, and install requests. The control plane fetches only public HTTPS URLs accepted by the import policy, rejects embedded credentials, fragments, and credential-like or signed-token query parameters, follows at most five same-host redirects, caps the response at 2 MiB, requires JSON-compatible content, and then runs the normal manifest schema and source checks. The remote manifest URL is not stored on the download record; the verified manifest payload is stored instead.

Authenticated downloads use encrypted secrets rather than URL credentials. Store a token in External Access with category `model-download`, then select that secret name in the Models tab download-token field or pass `credential_secret_name` to `POST /admin/models/downloads`. The control plane validates that the secret exists and has the `model-download` category before queueing the record. The background runner decrypts it only when making the outbound request, sends it as `Authorization: Bearer ...` only to the original manifest source host, preserves `Range` resume headers, validates resumed `Content-Range` and `Content-Length` before appending bytes, and never writes the plaintext token to the manifest, download record, audit metadata, or logs. Direct-url redirects must stay on the original source host. Hugging Face redirects may go only to Hugging Face or known HF/CDN hosts, and signed redirect URLs are not persisted. Stage blobs from Control Center, then publish the verified manifest.

Archive-format manifest files are supported for `.zip`, `.tar`, `.tar.gz`, `.tgz`, `.tar.bz2`, `.tbz2`, `.tar.xz`, and `.txz` blobs. Install planning inspects verified archive blobs before allowing installation. The inspector rejects absolute paths, Windows drive paths, `..` traversal, encoded path controls, malformed percent escapes, invalid percent-encoded UTF-8, duplicate overwrite paths, file/directory parent conflicts, symlinks, hardlinks, device nodes, FIFOs, encrypted zip entries, denied executable/code extensions, too many members, oversized members, and excessive uncompressed totals. Runtime-view creation never calls `extractall`; it creates directories and writes regular file bytes under the resolved view root with normalized permissions. Archive members are extracted relative to the archive file's manifest path parent, so a manifest file path of `bundle.zip` extracts at the model view root while `packs/bundle.zip` extracts under `packs/`.

Authoritative blob cleanup is intentionally staged. First quarantine the model record so runtime views are moved aside and aliases/dependencies are refreshed. Then use the blob quarantine plan to dry-run cleanup. The plan only becomes actionable when no active job, active runtime reservation, or active Voicebox voice profile references the model, the model record is not `installed`, every candidate blob verifies against the manifest, the blob is not referenced by any other model record, and the destination under `$B1_DATA_ROOT/models/quarantine/blobs` is unused. Applying the plan moves blobs into a recoverable quarantine directory. Runtime reservation dependency reports include only reservation ID, owner, runtime, model alias, immutable model version, and expiry; free-form reservation reasons and idempotency keys are not exposed.

Permanent deletion is a separate Storage operation. Use the Storage tab or `POST /admin/models/quarantine/retention-plan` to dry-run old quarantine-set cleanup, then `POST /admin/models/quarantine/cleanup` with `confirm=true` to delete only validated quarantine batches older than the requested age. The cleanup never scans or deletes active `$B1_DATA_ROOT/models/blobs` files or runtime views, and malformed quarantine entries are preserved for operator review.
