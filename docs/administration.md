# Administration

Control Center is served at `https://control.ai.b1.germering/`.

Initial administrative areas:

- Dashboard: service status, resource policy, queue waits, runtime URLs, runtime-agent health, GPU, memory, recent job timings, and model switches
- Models: aliases, installation status, runtime preference, visibility, idle timeout, resource policy
- Runtimes: LocalAI, ComfyUI, Voicebox, and CPU audio state
- Queue and jobs: durable media job records and SSE status
- Workflows: published workflow registry
- External access: API clients, Model Hub clients, encrypted secrets, compatibility endpoints
- Storage: model, artifact, cache, and backup usage
- System: TLS, maintenance, updates, rollback, bounded service logs, audit logs

The UI must not expose arbitrary shell, Docker, host path, or download destination controls.

## Dashboard Observability

The Dashboard reads `GET /admin/status` for configuration and `GET /admin/metrics` for live operational summaries. The metrics endpoint intentionally stays lightweight for the 32 GB target: it aggregates recent durable job rows in PostgreSQL, scheduler ownership, runtime states, and runtime-agent telemetry instead of requiring Prometheus or Grafana for first boot. Administrators who want scraper-friendly metrics can use the same authenticated snapshot at `GET /admin/metrics.prometheus`, which returns Prometheus text exposition without prompt, owner, job, artifact, path, credential, or model-identifier labels.

Operators can see queue depth, active jobs, oldest wait, recent run-time p95, completed/failed/cancelled jobs in the last hour, model switches per hour, peak RAM/VRAM recorded on jobs, host memory/swap, and normalized GPU memory/utilization/temperature. If runtime-agent telemetry is unavailable, the Dashboard shows the error and continues to display database-backed queue and job information.

## Browser Sign-In

Control Center and Media Studio authenticate through the control-plane `/auth/*` endpoints. First boot creates the initial administrator from the web UI after the operator enters the generated bootstrap key. Later sessions use username/password login, an HttpOnly session cookie, and the CSRF token returned by `/auth/status` or `/auth/login`. The UIs automatically include `X-B1-CSRF` on mutating requests. Service clients should use scoped bearer tokens instead of browser sessions.

## API Clients

Administrators create scoped API clients from Control Center or the `/admin/api-clients` API. API client and Model Hub sync-client management is administrator-only because these routes issue or mutate credentials. The full key is shown once and only a salted hash is stored.

`client_open_webui_internal` is system-managed. It is provisioned from `$B1_DATA_ROOT/secrets/open_webui_api_key` during control-plane startup and is the only key Open WebUI should use for the unified API. If this key must be rotated, update the generated secret and restart Open WebUI plus the control plane so the container environment and stored hash agree.

Roles:

- `admin`: full administrative access
- `operator`: model, runtime, job, workflow, and storage operations
- `creator`: workflow and job operations
- `user`: ordinary inference and job operations
- `service`: external automation, Model Hub sync, and inference clients

## Encrypted Secrets

The External Access tab includes administrator-only encrypted value management for remote-provider credentials, model-download tokens, runtime credentials, and integration secrets. Values are encrypted by the control plane with AES-GCM before PostgreSQL storage. The UI clears the value after save and later shows only metadata: name, display name, category, envelope scheme, key fingerprint, update time, and deletion status.

Secret names must use letters, numbers, `.`, `_`, `:`, or `-` and begin with an alphanumeric character. Normal operations are list, store/update, verify, and delete. Verify decrypts the value server-side and returns only `status=verified`; it never returns the plaintext. Delete is a soft delete so the row remains recoverable from logical database backups.

The generated master key lives outside Git at `$B1_DATA_ROOT/secrets/master_encryption_key` and is mounted as `/run/secrets/master_encryption_key`. Restoring encrypted values onto another host requires restoring that key file as well as the PostgreSQL logical export or native dump.

## Models

The Models tab reads `GET /admin/models` and shows public aliases, resolved immutable model versions, runtime preference, persisted alias policy, resource labels, runtime view targets, and database model records. Operators can enable/disable an alias, choose a compatible preferred-runtime override, set an idle timeout, restrict role visibility, and reset the row back to seed defaults without editing files. A blank idle timeout uses `B1_GPU_DEFAULT_IDLE_TIMEOUT_SECONDS`, default 300 seconds. Disabling refuses active jobs and makes inference calls fail before model loading. Role-restricted aliases are hidden from `/v1/models` and rejected for callers outside the allowed roles while remaining visible to administrators in Control Center. Operators can plan an installation before publishing a manifest. The plan displays source, licence, total size, resource decision, runtime view paths, and each required blob's verification status.

The same tab can plan and queue supported direct-url model downloads. Download records are durable, resumable from `.partial` files, cancellable, and show aggregate byte progress plus final error categories. Administrators can store bearer tokens as encrypted secrets in category `model-download`; the Models tab lets operators attach one by secret name before queueing the download, and public records show only that the download is authenticated. A queued download stages only the content-addressed blobs; operators still publish the model after every blob verifies so licence/resource information remains visible before activation.

Installation currently publishes only manifests whose content-addressed blobs are already present and verified under `$B1_DATA_ROOT/models/blobs`. It creates hardlinks into `$B1_DATA_ROOT/models/runtime-views/{runtime}`, records the model in PostgreSQL, refreshes the catalog overlay, recalculates workflow dependency readiness, and writes an audit event. Operators can request an immediate smoke test during installation or run one later from the installed model record. Successful smoke tests store a `measurements` history in the model manifest and update the admission `resource_estimate` conservatively from measured peak RAM/VRAM. Quarantine refuses active jobs, reports dependent workflows, moves runtime views to recoverable quarantine, marks the database record `quarantined`, refreshes dependencies, and leaves authoritative blobs in place.

After a record is quarantined, the Models tab can dry-run authoritative blob quarantine and then apply it with explicit confirmation. The cleanup plan refuses shared blobs, active job references, symlinks, missing files, size or SHA-256 mismatches, and existing quarantine destinations. Applying the plan moves verified unused blobs to `$B1_DATA_ROOT/models/quarantine/blobs/{model_id}/{version-timestamp}` and records the action in the audit log.

## Scheduler Ownership

The scheduler lease API records the active GPU scheduler owner, epoch, and expiry. It is an administrative diagnostic and recovery surface for the one-GPU policy. Normal runtime acquisition uses both the durable PostgreSQL owner row and an expiring Redis live-owner key. If Redis is configured but cannot grant the matching owner key, the control plane fails the lease attempt closed and releases the PostgreSQL claim instead of running a GPU pipeline on a partial lease.

Runtime reservations are persisted in PostgreSQL as scheduler intent records. A reservation validates the requested alias/runtime pair, records the resolved immutable model version, owner, reason, duration, and expiry, and can be cancelled without touching any runtime container. Creating a reservation is rejected while a conflicting active reservation for another owner/runtime/model holds the single-GPU window. While an active reservation exists, queued GPU jobs are claimable only when their owner, runtime, and immutable model version match an active reservation. Synchronous GPU inference requests perform the same reservation gate before acquiring the scheduler lease. Expired reservations are marked `expired` during scheduler checks.

The Jobs tab shows a filterable reservation table, the current GPU scheduler lease, and controls for creating or cancelling a time-bounded reservation. The fleet reservation list is administrator/operator-only; direct reservation reads and cancellations remain owner-scoped unless the caller has administrative privileges.

## Resource Policy

The System tab exposes the effective RTX 3060/32 GB resource policy. Administrators can load the environment defaults, edit the bounded fields, dry-run validation, save a database override, or reset back to the environment profile. The persisted row is included in the control-plane logical PostgreSQL export.

Hard bounds are derived from the environment-defined physical profile, so the default installation cannot raise GPU memory above 12 GiB or host RAM above 32 GiB from the browser. The one-GPU safety policy keeps `gpu_max_active_pipelines=1`, `comfyui_maximum_parallel_jobs=1`, and `comfyui_maximum_batch_size=1`. Updating the policy refreshes catalog resource-admission labels and updates the live GPU runner's VRAM reserve without a restart.

## Admission Policy

The System tab also exposes the effective media admission policy. Administrators can dry-run validation, save a database override, or reset back to the environment defaults for owner queue depth, owner active jobs, owner hourly job rate, global queued jobs, artifact-root byte cap, and filesystem free-space reserve. The persisted row is included in the control-plane logical PostgreSQL export and reloaded on control-plane restart.

Dashboard and Storage show the live admission snapshot from `GET /admin/admission`. Queue/rate counters come from durable PostgreSQL job rows. Artifact headroom is checked before accepting new uploads or media jobs; use generated-artifact retention cleanup to reclaim space when new work returns HTTP 507.

## Maintenance Mode

The System tab also manages persisted maintenance mode. Enabling it requires an administrator role, `admin:write`, and a reason. The state is stored in PostgreSQL, included in `/admin/status`, exported in logical database backups, and reloaded by the control plane on restart.

While maintenance mode is active, the control plane rejects new synchronous inference requests, staged media uploads, new media jobs, native ComfyUI `POST /prompt` submissions, runtime reservations, and admin job retries with HTTP 503. CPU, GPU, and model-download background runners also pause before claiming queued work, so queued jobs/downloads wait until maintenance is disabled while any already active non-preemptable work can finish its current safe unit. Existing job reads, event streams, artifact reads, cancellation, priority changes, backups, restore tests, audit inspection, model administration, and runtime inspection remain available so operators can drain work and complete a controlled update or rollback window.

## Controlled Updates

The System tab records controlled update plans. Administrators provide a target version, optional HTTPS release URL, notes, and one or more service image references pinned by `@sha256:<digest>`. The control plane rejects `latest`, missing digests, duplicate services, unsafe service names, source URLs with credentials, and non-HTTPS source URLs.

Staging an update requires maintenance mode. The stage action creates a normal constrained backup, sends each pinned service image to runtime-agent `/v1/images/{service}/pull`, records the per-image result on `image_stage`, writes a digest-pinned Compose override to `$B1_DATA_ROOT/data/control-plane/updates/<update_id>/compose.images.yaml`, runs the same self-test used by `/admin/self-test`, and stores the backup name, override metadata, and self-test result on the update row. The override sets `image:` for each staged service and `build: null` so a controlled Compose invocation can consume the pulled immutable images instead of rebuilding local contexts.

With the default `B1_ENABLE_MUTATIONS=false`, image staging is a dry run. In that case the override is still generated, but it is marked `ready_for_promotion=false` and lists the services that still require an actual pull before promotion. When mutations are explicitly enabled during a maintenance window, runtime-agent pulls only the allowlisted service images pinned by digest; if all selected services report a real pull/already-present status, the override is marked ready.

After the update is staged and health-checked, the Promote action verifies the stored override path, SHA-256, service list, image-stage results, and runtime-agent image inspection results before writing `promotion_result` to the update row. The handoff includes the fixed Compose command:

```bash
docker compose -f compose.yaml -f /srv/b1-ai-hub/data/control-plane/updates/<update_id>/compose.images.yaml up -d --no-build <services...>
```

Run that command from the repository root during the same maintenance window, then run Health-check again from Control Center. The control-plane image runs Alembic migrations before serving traffic, and health-check re-runs the self-test after the promoted image starts. Rollback calls only the predefined runtime-agent `/v1/rollback` action and stores whether the result was an actual rollback or the default dry-run plan. The update surface is a safe control record, image artifact, promotion preflight/handoff, migration-on-startup path, validation path, and rollback path; it does not expose arbitrary shell commands or Docker API passthrough.

## System Self-Test

The System tab runs `GET /admin/self-test`. The check verifies PostgreSQL, Redis, B1 data-root visibility, writable control-plane data, artifact temporary storage, backup storage, restore-test storage, runtime health endpoints, runtime-agent status, runtime-agent metrics, and GPU metric availability where `nvidia-smi` is present in the runtime-agent container.

The same report performs bounded end-to-end probes required for operator acceptance:

- `tls:routing` requests the configured HTTPS self-test URLs, defaulting to `https://$B1_HOST_API/healthz`. With the default Caddy internal CA, the control plane verifies TLS with `$B1_DATA_ROOT/data/caddy/pki/authorities/local/root.crt` when that file exists. Each route must also return the Caddy security headers `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Permissions-Policy`; this catches direct backend exposure or gateway configuration drift before cutover.
- `inference:tiny` runs a minimal `embedding-default` request and verifies the returned vector shape. If the scaffold CPU engine is disabled and no production embedding engine is configured, this fails rather than reporting a fake-ready inference path.
- `runtime-agent:unload` submits a `dry_run=true` unload request for `B1_SELF_TEST_UNLOAD_RUNTIME`, default `localai`, proving the mTLS/token/runtime-action path without restarting containers.
- `runtimes:production-readiness` classifies required runtime health. Development mode reports placeholders as a warning; production mode reports placeholders, missing runtimes, or unhealthy required runtimes as failed.
- `artifact:delivery` writes a temporary artifact probe, fetches it from `artifact-server` with the generated internal bearer token and an HTTP Range request, verifies the returned bytes, and removes the probe file.

Tune these probes with `B1_SELF_TEST_TLS_URLS`, `B1_SELF_TEST_TLS_CA_FILE`, `B1_SELF_TEST_TLS_VERIFY`, `B1_SELF_TEST_TINY_INFERENCE_ENABLED`, `B1_SELF_TEST_UNLOAD_RUNTIME`, `B1_RUNTIME_DEPLOYMENT_MODE`, and `B1_RUNTIME_PRODUCTION_REQUIRED`. A failed self-test during update staging marks the update stage as failed; a degraded self-test remains visible but does not block staging.

GPU/NVML metrics are reported as a warning when unavailable so a CPU-only development host can still use the rest of the appliance checks. On the target RTX host, missing GPU metrics indicate that NVIDIA host prerequisites or container runtime GPU visibility still need attention.

## Audit Log

The System tab also shows recent audit events from `GET /admin/audit-log`. The control plane stores successful administrative mutations in PostgreSQL, including API-client creation/revocation, scheduler lease acquisition, backup create/verify/restore-test/import actions, workflow publish/unpublish, job cancellation/retry/priority updates, runtime reservation create/cancel, and Model Hub client create/revoke.

Audit metadata is intentionally compact. It keeps public identifiers, target IDs, roles, status, and resource counts, while recursively redacting secrets, bearer tokens, prompts, messages, uploaded files, voice samples, images, audio, video, documents, and other sensitive payload fields before database insertion. Audit events are included in the logical PostgreSQL export generated before backups.

## Queue and Jobs

The Jobs tab uses `GET /admin/jobs` and is limited to administrators and operators. It can filter by state, runtime, modality, and owner, inspect a selected job's redacted request, native prompt ID, retry count, artifacts, timings, and measured RAM/VRAM fields, follow `GET /admin/jobs/{job_id}/events` for live durable job snapshots, and refresh the durable queue state without touching runtime containers.

Operators can update priority while a job is still in `created`, `validated`, `queued`, or `waiting_for_gpu`. Valid priorities are `chat`, `interactive_audio`, `single_image`, `image_batch`, `video`, and `batch`. Cancelling a queued/pre-run job marks it `cancelled`; cancelling an active job marks it `cancelling` so the runner or adapter can interrupt at a safe point. Retrying is available only for `failed`, `cancelled`, `expired`, or `recovery_required` jobs and requeues the same durable job with an incremented retry count and cleared failure/artifact/measurement fields.

Media Studio and API clients follow `GET /v1/media/jobs/{job_id}/events` for live progress. Event streams are long-lived for active work and close only when the client disconnects, the job disappears, authorization no longer permits access, or the job reaches `completed`, `cancelled`, `failed`, `expired`, or `recovery_required`. A recovery-required job therefore stops progress polling immediately and remains visible for operator retry or diagnosis instead of timing out as an active job.

On control-plane startup, runner reconciliation requeues jobs that had only been claimed into `waiting_for_gpu` and had not begun runtime preparation. Jobs interrupted while unloading, verifying VRAM, loading, warming, running, saving, or cancelling are marked `recovery_required` with a restart failure category and are not automatically replayed. This avoids duplicate media submissions after a restart; operators inspect and retry those jobs from the Jobs tab when it is safe.

Ordinary `/v1/media/jobs` access is owner-scoped. Service clients, creators, and users with `jobs:read` see only jobs they own unless they have wildcard administrative scope. The admin queue API is the intended surface for whole-system queue management.

## Runtimes

`GET /admin/runtimes` reports configured adapter capabilities, the `b1-runtime-adapter/v1alpha1` contract, and health for LocalAI, ComfyUI, Voicebox, CPU audio, and optional external adapters. The Control Center Runtimes tab shows modalities, operations, capability flags, contract version, and the scheduler, submit, event, lifecycle, metrics, unload, and recovery surfaces so operators can see whether a capability error came from the model manifest, the runtime adapter, GPU-lease management, native/WebSocket support, OpenAI-compatible forwarding, CPU-only residency, or external-data policy. External adapters remain disabled unless `B1_ALLOW_EXTERNAL_PROVIDERS=true`. Runtime health honors body-level statuses from adapters, so `audio-cpu` appears as `unconfigured` in Control Center and the system self-test when the scaffold engine is disabled by `B1_CPU_AUDIO_ENABLE_PLACEHOLDER=false`. The CPU runtime smoke hook follows the same policy and reports `status=unconfigured` without taking a GPU lease.

The same response includes a runtime readiness check. `B1_RUNTIME_DEPLOYMENT_MODE=development` keeps the mock topology bootable for implementation work but marks required placeholder, missing, or unhealthy runtimes as a warning, which makes the overall self-test degraded. Before cutover acceptance set `B1_RUNTIME_DEPLOYMENT_MODE=production`; then the `runtimes:production-readiness` check fails until every runtime listed in `B1_RUNTIME_PRODUCTION_REQUIRED` is healthy and does not report `placeholder=true` or a `placeholder-*` runtime kind. The default required set is `localai comfyui audio-cpu`; add `voicebox` when the optional Voicebox profile is part of the deployed service level.

External runtime adapters are fail-closed. Setting `B1_ALLOW_EXTERNAL_PROVIDERS=true` only makes external adapters visible and eligible after their base URL validates. Administrators can manage `openai-compatible` and `generic-http` from the Runtimes tab or `/admin/runtimes/external-config`; a database row overrides environment fallback values. `B1_OPENAI_COMPATIBLE_BASE_URL` and `B1_GENERIC_HTTP_BASE_URL` remain bootstrap/environment fallbacks and must use HTTPS, must not embed credentials, query strings, fragments, relative path segments, or private/loopback/link-local/reserved IP literals. OpenAI-compatible remote credentials may be referenced by encrypted secret name from category `remote-provider`; the adapter decrypts them server-side, sends them as bearer tokens, and never returns the key in `/admin/runtimes` or `/admin/runtimes/external-config`. Enabling a row requires `confirm_external_data=true` because prompts, media, voices, documents, and metadata may leave the LAN. Unconfigured external adapters are not selected by alias resolution, so enabling external providers without a safe URL produces a clear capability error rather than an attempted `disabled://` request.

Runtime selection is deterministic: the resolver uses a valid persisted alias preferred-runtime override first, then the manifest preferred runtime when it satisfies policy, otherwise the first compatible runtime listed by the manifest. Durable jobs record the selected runtime and immutable model version so later scheduler recovery does not depend on mutable aliases.

Installed chat, responses, and embedding aliases that resolve to an OpenAI-compatible runtime such as LocalAI or the lightweight `audio-cpu` embedding path are forwarded from the unified API to the internal runtime. GPU-backed synchronous calls acquire the global scheduler lease, ask the other GPU runtimes to unload through their `/b1/runtime/unload` hooks before falling back to runtime-agent restart, verify VRAM policy, call the selected runtime's optional load/warm hooks, then release the lease after the request or stream finishes. Streaming responses renew that lease until completion. Explicit hook failures return HTTP 503 with `detail.type=runtime_prepare_failed` and the runtime, public alias, and immutable model version; the request is not forwarded to the runtime. The default stream-safe lease TTL is `B1_SYNC_INFERENCE_LEASE_TTL_SECONDS=7200`. If a synchronous OpenAI-style endpoint resolves to a non-compatible runtime, the request fails with a capability error instead of a placeholder response.

When queued GPU work or a synchronous GPU-backed request finishes, the control plane marks the runtime idle with the active alias and immutable model version. The GPU runner checks this state only while no GPU job is claimable. If the alias-specific idle timeout or default timeout has expired, it acquires the same scheduler lease, calls the runtime's `/b1/runtime/unload` hook, and falls back to runtime-agent unload only when the hook does not confirm success. Runtime-agent mutations are disabled by default in development mode, so dry-run fallback unloads remain visible as unconfirmed runtime state; production deployments must enable approved runtime mutations for restart-based fallback recovery. Confirmed admin unloads clear the active runtime-state model; unconfirmed unloads leave it visible for retry.

The Runtimes tab also manages Voicebox profiles. Administrators and operators can create profile records with a runtime (`voicebox` or `audio-cpu`), engine ID, TTS model alias, profile type, status, visibility roles, bounded metadata, and references to already-managed audio artifacts. The control plane rejects non-TTS aliases, runtime mismatches, and inline voice/audio/base64 fields in metadata. Export and delete operations are audited; deletion is a soft delete so profile metadata remains recoverable from PostgreSQL backups.

## Runtime Agent

The runtime-agent is internal-only and defaults to mutual TLS on `https://runtime-agent:8443` plus the generated `$B1_DATA_ROOT/secrets/runtime_agent_token` bearer token. Bootstrap creates a private runtime-agent CA, server certificate, and control-plane client certificate under `$B1_DATA_ROOT/secrets`; Compose mounts them read-only into both services. `/healthz` stays unauthenticated for container health checks, but every `/v1/*` endpoint fails closed if the runtime-agent bearer token is missing, malformed, or not presented. `B1_RUNTIME_AGENT_ALLOW_MISSING_AUTH=true` is a development-only escape hatch and must remain false for deployment and cutover validation. `GET /v1/status` reports socket/API reachability, mTLS posture, token posture, `GET /v1/services` reports allowlisted Compose-service containers, `GET /v1/metrics` reports CPU, memory, disk, and optional `nvidia-smi` GPU metrics, and `GET /v1/services/{service}/logs` returns bounded redacted Docker logs. Operators read logs through the Control Center System tab or `GET /admin/services/{service}/logs`; browsers never call runtime-agent directly.

Start, stop, and restart endpoints exist only for immutable allowlisted B1 services. Runtime `recover` and `unload` actions are a narrower predefined subset controlled by `B1_RUNTIME_ACTION_SERVICES`; the current forced-unload strategy is a bounded restart of the selected runtime service. Runtime-agent also exposes `/v1/images/{service}/inspect` and `/v1/images/{service}/pull` for controlled update staging. Those endpoints refuse non-allowlisted services, missing digests, and `latest` tags; pull is dry-run unless mutations are explicitly enabled. `/v1/rollback` is a predefined restart plan controlled only by `B1_ROLLBACK_SERVICES`; request bodies cannot add services or commands. Mutation endpoints return dry-run responses by default because `B1_ENABLE_MUTATIONS=false`, and `dry_run=true` remains non-mutating even after actual mutations are enabled. Real mutation attempts are capped by `B1_RUNTIME_AGENT_MUTATION_RATE_LIMIT_PER_MINUTE`, default `12`, and the runtime-agent writes structured JSON mutation audit events to its own service logs with secret-like values redacted from reasons. To enable actual Docker mutations during a controlled maintenance window, set `B1_DOCKER_GID` to the host Docker group GID, set `B1_ENABLE_MUTATIONS=true`, and keep mTLS plus the runtime-agent token in place. `B1_RUNTIME_AGENT_MTLS_ENABLED=false` and `RUNTIME_AGENT_URL=http://runtime-agent:8000` are development-only escape hatches. The API still refuses non-allowlisted service names and does not expose arbitrary Docker calls.

## CPU Job Runner

The CPU job runner is enabled by `B1_JOB_RUNNER_ENABLED=true`. It only processes jobs resolved to `audio-cpu`, so it does not take or bypass the GPU lease. On startup it marks interrupted active CPU jobs as `recovery_required`; only pre-runtime `waiting_for_gpu` claims are automatically requeued by the shared reconciliation path. For TTS jobs it calls the internal `audio-cpu` `/v1/audio/speech` endpoint and stores the returned WAV/audio bytes under `$B1_ARTIFACT_ROOT/audio-cpu/...`; for STT jobs it calls `/v1/audio/transcriptions`, requires a `text` field, and stores the transcript JSON as an artifact. CPU jobs record `started_at` and `run_time_ms`; resource peak fields stay empty unless a later CPU metrics sampler fills them. The default `B1_CPU_AUDIO_ENGINE=scaffold` is smoke-test only: successful scaffold responses carry `b1_placeholder=true` or `X-B1-Placeholder: true`, and setting `B1_CPU_AUDIO_ENABLE_PLACEHOLDER=false` makes scaffold speech, transcription, and embedding calls return HTTP 503 until real pinned CPU engines are configured.

`B1_CPU_AUDIO_ENGINE=piper` enables the first real CPU TTS adapter path. The default `audio-cpu` build installs rhasspy/piper `2023.11.14-2` into `/opt/piper/piper` with a pinned SHA-256; set `B1_INSTALL_PIPER=false` only when supplying an equivalent pinned derived image. Piper voice weights are installed as normal Model Hub artifacts. The catalog seeds `b1-piper-en-us-amy-low` as an available recommendation with two checked files; after installation, the control plane forwards `b1_resolved_model_version` and `audio-cpu` resolves the matching read-only runtime view under `/srv/b1-ai-hub/models/{model}/{version}`. `B1_PIPER_MODEL_PATH` remains only an optional static fallback for a single manually selected voice. Absolute paths outside the model root, symlinks, missing files, ambiguous ONNX files, unsafe model refs, and ONNX files without a matching Piper `.onnx.json` config leave the selected speech request `unconfigured`.

`B1_CPU_EMBEDDING_ENGINE=onnx` enables the first real CPU embedding adapter path. The default `audio-cpu` image includes pinned `onnxruntime`, `tokenizers`, and `numpy` wheels plus `libgomp1`; model weights still come from Model Hub. The catalog seeds `b1-minilm-l6-v2-onnx-q4` as an available recommendation with exact checksums for `tokenizer.json`, ONNX graph, and external data sidecar. After installation, `/v1/embeddings` forwards `b1_resolved_model_version`, loads the selected read-only runtime view, tokenizes locally, runs ONNX Runtime on CPU, applies mean pooling and L2 normalization, and returns OpenAI-compatible embedding arrays with `b1_embedding_engine=onnxruntime` and `b1_placeholder=false`. `dimensions` may request a truncated normalized prefix for lightweight self-tests; the native model output is 384 dimensions.

`B1_CPU_STT_ENGINE=vosk` enables the first real CPU STT adapter path. The default `audio-cpu` image includes pinned `vosk==0.3.45`; model weights still come from Model Hub. The catalog seeds `b1-vosk-small-en-us-0.15` as an available recommendation with the official zip SHA-256 recorded in the manifest. Installation safely extracts that archive into the `audio-cpu` runtime view, and `/v1/audio/transcriptions` forwards `b1_resolved_model_version` so the runtime selects exactly that installed model. The initial Vosk path accepts JSON base64 audio, multipart `file` uploads normalized by the control plane, or raw request bodies normalized by the control plane, but the runtime currently decodes only bounded mono signed 16-bit PCM WAV. It rejects unsupported channels, sample widths, sample rates outside `8000..48000`, oversized payloads, and overlong durations before invoking Vosk. Tune limits with `B1_VOSK_STT_MAX_AUDIO_BYTES`, `B1_VOSK_STT_MAX_AUDIO_SECONDS`, `B1_VOSK_STT_WORDS`, and `B1_VOSK_STT_LANGUAGE`. `B1_VOSK_STT_MODEL_PATH` is only an optional static fallback under the model root for one manually selected model.

Model smoke tests call `audio-cpu` `/b1/runtime/smoke` with the generated runtime-control bearer token, exercise the selected CPU modality, report zero VRAM use, and return `status=unconfigured` when the selected operation has no configured engine. The audio-cpu hook rejects missing or wrong runtime-control tokens when `B1_RUNTIME_CONTROL_REQUIRE_AUTH=true`, while normal `/healthz`, speech, transcription, and embedding requests keep their existing internal API behavior. Unknown `audio-cpu` job shapes fail with `failure_category=unsupported_audio_cpu_operation` and no artifact, so unsupported work cannot be mistaken for a successful generated result.

## GPU Job Runner

`B1_GPU_JOB_RUNNER_ENABLED=true` enables a control-plane runner for `localai`, `comfyui`, and `voicebox` media jobs. It claims queued or waiting GPU jobs, acquires the PostgreSQL-plus-Redis scheduler-owner lease, records the required unload/VRAM/load/warm/run states, records `started_at`, `load_time_ms`, `run_time_ms`, and runtime-agent peak VRAM/RAM values where available, verifies VRAM policy, and releases the lease after the job is complete or safely failed. If another owner holds the lease, the job remains in `waiting_for_gpu` for the next pass.

Claim selection uses the scheduler priority classes `chat`, `interactive_audio`, `single_image`, `image_batch`, `video`, and `batch`, with an aging bonus so long-waiting background work can eventually overtake newer interactive work. Unknown priority values are treated as `batch`. Reservation gates are applied before this ranking, so an active reservation first narrows the eligible GPU jobs to its owner/runtime/model.

During `unloading`, the runner asks every other GPU runtime to release its active model through `/b1/runtime/unload` before the target runtime is prepared. If that graceful hook is missing, unreachable, or unconfirmed, it asks runtime-agent to run the predefined `unload` action for the runtime service as a bounded restart fallback. During `loading` and `warming`, it calls optional internal runtime hooks at `/b1/runtime/load` and `/b1/runtime/warm` on the selected runtime URL with the job ID, selected runtime, public alias, immutable model version, modality, operation, and resolved model ID. Runtimes that do not implement those hooks may return 404/405 or be temporarily unreachable; the runner treats that as unsupported and continues to the adapter-specific submission path. A runtime that implements the hook but returns another HTTP error or an explicit failure-like hook status such as `failed`, `error`, `unconfigured`, `invalid`, or `unhealthy` fails before inference with `failure_category=runtime_prepare_failed`. The runner records these scheduler-observed runtime states in PostgreSQL and exposes them in Control Center runtime cards; the records intentionally omit prompts, media, and request parameters.

For jobs resolved to `comfyui`, the runner now submits a native ComfyUI `/prompt` payload when the job input contains `comfyui_payload`, `comfyui_prompt`, `native_prompt`, `workflow_json`, or references a published workflow with non-empty `workflow_json`. Optional `input.parameters` values can fill `{{parameter}}`, `{{parameters.name}}`, `$parameters.name`, or `$input.name` placeholders in the native graph before submission. The runner records `native_prompt_id`, polls `/history/{prompt_id}`, ingests returned images/audio/video from ComfyUI `/view` into `$B1_ARTIFACT_ROOT/comfyui/...`, stores SHA-256 and byte metadata, and marks the durable job complete. If history does not appear before timeout or artifact storage fails, the job becomes `recovery_required`.

For image generation jobs resolved to `localai`, the runner submits an OpenAI-compatible JSON request to LocalAI `/v1/images/generations` with the resolved immutable model ID. Image edit jobs resolved to `localai` use staged uploads or image data URLs for the `image` and optional `mask` fields and submit them as multipart files to LocalAI `/v1/images/edits`. Text-to-video jobs submit JSON to `/v1/videos/generations`; image-to-video jobs submit staged or data-URL `image` input as multipart to `/v1/videos/image-to-video`, with workflow fields such as `source_image` mapped through `runtime_parameter_mappings` when needed. These LocalAI media paths store returned `b64_json`, `b64`, `base64`, `data:` URL, or same-origin runtime URL media under `$B1_ARTIFACT_ROOT/localai/...` with SHA-256 and byte metadata. If LocalAI returns no downloadable media, the job becomes `recovery_required` instead of receiving a placeholder success.

For TTS jobs resolved to `voicebox`, the GPU runner calls the internal Voicebox `/v1/audio/speech` endpoint after the global GPU lease has been acquired, rewrites the public alias to the resolved immutable model ID, stores the returned audio under `$B1_ARTIFACT_ROOT/voicebox/...`, and fails to `recovery_required` if Voicebox returns an empty response. The synchronous OpenAI-compatible `/v1/audio/speech` route follows the same alias resolution; CPU aliases proxy to `audio-cpu` without a GPU lease, while GPU-backed Voicebox or OpenAI-compatible runtimes proxy only after the scheduler lease and runtime preparation path complete.

Native ComfyUI `POST /prompt` compatibility traffic still uses the inline proxy path rather than the media runner. It creates a durable `workflow/comfyui-prompt` job inline, waits for the same global scheduler lease, asks runtime-agent to unload other GPU runtimes, verifies the VRAM reserve, calls ComfyUI's load/warm hooks when present, forwards the native request unchanged after admission succeeds, records admission `load_time_ms`, records the native `prompt_id`, and then a background tracker renews the lease until the prompt appears in ComfyUI history or the configured timeout is reached. The production ComfyUI image installs those hooks as the B1 `b1_runtime_hooks` custom-node package; development or third-party ComfyUI images may still report them as unsupported. Explicit load/warm hook failures return HTTP 503 with `detail.type=runtime_prepare_failed`, leave the native prompt unsubmitted, and mark the durable job with `failure_category=runtime_prepare_failed`. The tracker records `run_time_ms` for completed, cancelled, timeout, and recovery-required outcomes, and it marks ComfyUI idle after confirmed completion or cancellation so alias/default idle timeout cleanup can unload it later.

When runtime-agent GPU metrics are available, the runner verifies measured VRAM during `verifying_vram`. If memory remains above the configured reserve, it asks runtime-agent to recover the target runtime through the predefined bounded action, then verifies again. The job fails safely when VRAM is still above reserve, which is expected on hosts where `B1_ENABLE_MUTATIONS=false` and a runtime is already holding memory. GPU jobs whose selected runtime does not implement the requested modality/operation fail with `failure_category=unsupported_gpu_operation` and no artifact, including non-speech Voicebox media requests until their model-specific adapters exist. Upstream runtime images still need real model-aware implementations behind the optional load/warm/smoke hooks before production GPU acceptance tests can pass.

## Workflows

The control plane imports approved workflow seed files from `$B1_WORKFLOW_SEED_DIR` into PostgreSQL on startup. The default seed directory is `/opt/b1/workflows/approved`, mounted read-only from the repository. Runtime-edited workflow state belongs in PostgreSQL and the external workflow data directory, not in the source tree.

Published workflow records include native workflow JSON, input/output JSON Schemas, execution modality/operation/model alias, runtime policy, output MIME types, dependency declarations, limits, visibility roles, backend policy, resource class, optional `comfyui_parameter_mappings`, and optional `runtime_parameter_mappings`. A ComfyUI mapping writes a validated `input.parameters` value into a JSON path inside the ComfyUI API graph, for example `{"parameter":"prompt","path":["6","inputs","text"]}`. A runtime mapping renames a validated workflow field before adapter submission, for example `{"runtime":"localai","parameter":"source_image","target":"image"}` for LocalAI image edits. Mapped source fields are removed by default unless `keep_source=true`. Validation checks identifier shapes, schema structure, role values, limit bounds, MIME types, dependency types, runtime availability, model alias installation state, approved ComfyUI custom-node pins, and that mappings only reference declared input-schema properties with safe bounded paths or adapter parameter names.

Custom ComfyUI node approval is separate from workflow publication. The committed registry at `workflows/approved-node-pins.json` is mounted read-only at `$B1_COMFYUI_NODE_PIN_REGISTRY` as bootstrap seed data, while administrator-approved runtime state is stored in PostgreSQL as `b1_comfyui_node_pins`. Database rows override matching seed rows, so an administrator can disable or supersede a seeded approval without editing Git files. Each pin records an exact `(node id, git commit)` pair, HTTPS repository URL, status, approver metadata, optional dependency-lock digest, and optional `allowed_route_prefixes` for audited mutating custom APIs. A workflow that declares a `node` dependency without a 40-character commit pin is rejected; a workflow pinned to a missing, disabled, or superseded registry entry remains visible but non-publishable with `status: needs_dependencies`. A custom mutating route is forwarded only when the request path matches both `B1_COMFYUI_TRUSTED_ROUTE_PREFIXES` and an approved pin's `allowed_route_prefixes`.

The Workflows tab lists published workflow versions, readiness, backend policy, model alias, dependency status, and the merged ComfyUI node-pin registry. Creators/operators can inspect pins; administrators can approve new pins or update existing seed/database pins from the browser through `POST /admin/comfyui/node-pins` and `PATCH /admin/comfyui/node-pins/{node_id}/commits/{commit}`. Operators can load a JSON file, edit the workflow JSON in the browser, validate it through `POST /workflows/v1/validate`, publish through `POST /workflows/v1/published`, or unpublish a version through `DELETE /workflows/v1/published/{id}/versions/{version}`. The UI does not write repository seed files; runtime workflow and custom-node approval state remains in PostgreSQL and is included in logical backups.

Seed placeholders can remain published with `status: needs_dependencies`; that state is intentional and tells Media Studio and Control Center which model/runtime dependencies must be installed before execution.

## Media Studio

Media Studio reads `GET /workflows/v1/published`, renders each workflow's input JSON Schema as a form, submits `POST /v1/media/jobs` with the workflow's modality, operation, model alias, runtime policy, and parameter payload, streams job state from `GET /v1/media/jobs/{job_id}/events`, supports cancellation, and downloads durable artifacts through authenticated requests. File fields declared with `contentEncoding=base64` are uploaded first through `POST /v1/media/uploads`; the returned staged reference is stored in the job parameters and shown with a local preview. The active-job panel, history table, and history detail view show the resolved backing as local or external and ComfyUI-backed or non-Comfy-backed after the control plane selects the runtime. The control plane revalidates workflow ID/version, visibility, dependency readiness, modality, operation, model alias, runtime policy, JSON Schema fields, inline base64 media or staged-upload references, MIME type, staged size, and workflow resource limits before a workflow-backed job is queued.

## Backups

The Storage tab can create backups, list existing backup manifests, inspect a selected manifest's archive metadata, PostgreSQL dump records, sensitive file entries, largest included files, and raw JSON, verify archive/file checksums, run a restore test into `$B1_RESTORE_TEST_ROOT/<backup-name>`, plan retention cleanup, apply that cleanup with explicit confirmation, plan generated-artifact cleanup, apply generated-artifact cleanup with explicit confirmation, inspect admission limits/headroom, and manage a scheduled backup policy. The control plane is mounted only to the B1 appliance data root and does not accept arbitrary source or target paths from the browser.

Before archiving, the control plane exports its PostgreSQL tables to `data/control-plane/postgres-logical-export.json` and writes a native custom-format `data/control-plane/postgres-native.dump` with `pg_dump`. The backup archive includes those PostgreSQL dumps, Open WebUI data, control-plane data, Voicebox data, Caddy data/PKI, non-redownloadable model directories, blob quarantine staging, workflows, selected artifacts, generated secrets, and service logs. It excludes active reproducibly downloadable blobs, runtime views, caches, previous backups, restore-test output, and live PostgreSQL/Redis data directories. With `B1_BACKUP_ENCRYPTION_MODE=copy`, the control plane also writes an encrypted `payload.tar.gz.aesgcm` suitable for off-host storage; `encrypted-only` removes the plaintext payload and requires the restored master key for verification and restore.

Backup retention cleanup preserves the newest configured backup count, optionally filters candidates by age, reports invalid backup entries without deleting them, and removes only validated direct child backup directories under `$B1_BACKUP_ROOT`. Generated-artifact retention considers only terminal job artifacts older than the configured cutoff, can be limited to generated namespaces such as `localai`, `comfyui`, `audio-cpu`, or `voicebox`, preserves protected Voicebox profile sample artifacts, refuses symlinks and paths not scoped to the job or native ComfyUI prompt ID, and marks job artifact metadata as deleted after reclaiming the file. Deleted artifact downloads return HTTP 410 while the durable job record remains inspectable.

Admission limits are shown on Dashboard and Storage from `GET /admin/admission`. The System tab manages persisted admission overrides; the environment variables `B1_MAX_QUEUED_JOBS_PER_OWNER`, `B1_MAX_ACTIVE_JOBS_PER_OWNER`, `B1_MAX_JOBS_PER_HOUR_PER_OWNER`, `B1_MAX_QUEUED_JOBS_GLOBAL`, `B1_ARTIFACT_STORAGE_RESERVE_BYTES`, and `B1_ARTIFACT_STORAGE_MAX_BYTES` remain the reset defaults.

The scheduled backup policy stores `enabled`, `interval_hours`, `keep_last`, optional `delete_older_than_days`, and a safe `label_prefix` in PostgreSQL. The background scheduler is enabled by `B1_BACKUP_SCHEDULER_ENABLED=true`, wakes at `B1_BACKUP_SCHEDULER_INTERVAL_SECONDS`, atomically claims a due schedule row, creates a normal backup with PostgreSQL logical and native custom-format dumps plus configured archive encryption, applies the stored retention policy, records schedule status, and writes a system audit event. The Storage tab can also run that scheduled policy immediately. Restore-test extraction verifies archive checksums and runs `pg_restore --list` for native dumps. After restore-test extraction, Control Center can request a non-destructive PostgreSQL logical import plan, show table upsert operations, and apply the import after the administrator enters the exact backup name. Applying still requires maintenance mode and the server-side `confirm_backup_name` match; the importer upserts rows by primary key after migrations have created the target schema.

## Model Hub Clients

The External Access tab lists general API clients and dedicated Model Hub clients, creates new scoped keys, shows the generated key once, updates CIDR allowlists, and revokes active clients. General API clients can be source-network constrained with a CIDR allowlist at creation time or updated later; the control plane enforces that list on bearer-token authentication. Dedicated Model Hub clients are also available from the Model Hub API, not by hand-editing keys. Creation generates a service API key with only `modelhub:read` and `modelhub:sync`, stores the hash in the API-client table, and stores the Model Hub client allowlist separately. Revocation disables both records.

Use explicit `allowed_models` values for workstations and automation wherever practical. `["*"]` is accepted for trusted administrators but should not be the default for ordinary external machines. The External Access tab can update a Model Hub client's allowed models and `allow_downloads` policy after key creation; use catalog-only mode when a client should inspect available models but not download blobs. CIDR allowlists are enforced for general API clients at authentication time and for dedicated Model Hub clients on both their backing API key and their catalog/model/sync-plan/blob policy row; updating a Model Hub client's CIDR list updates both records atomically. Leave the CIDR list empty only for clients that are intentionally unrestricted by source network. The sync planner and blob endpoint both enforce downloadable-catalog policy; inference-only manifests remain visible but are skipped or rejected for blob download.

CIDR decisions use the direct control-plane peer address unless that peer is inside the active trusted proxy CIDR policy, in which case the first `X-Forwarded-For` or standard `Forwarded` `for=` value is used. The environment default `B1_TRUSTED_PROXY_CIDRS` trusts loopback and common Docker-internal proxy ranges so Caddy can pass the real LAN client address. If you configure static Docker IPAM, tighten trusted proxy CIDRs from the System tab or reset to the environment value during maintenance.

## Network Policy

The System tab manages the persisted network policy used by the control plane. CORS origins are explicit `http(s)://host[:port]` origins; wildcard and `null` origins are rejected because the browser APIs use credentials. Trusted proxy CIDRs control which direct peers may supply forwarded client IP headers for API-client and Model Hub CIDR checks. Saving updates the live control-plane cache immediately, and reset returns to `B1_CORS_ALLOW_ORIGINS` plus `B1_TRUSTED_PROXY_CIDRS` from the Compose environment.
