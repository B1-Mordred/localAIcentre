# Architecture

B1 AI Hub is a LAN-internal Docker Compose appliance. Caddy is the sole normal edge entry point. Open WebUI, Control Center, Media Studio, Model Hub, native ComfyUI compatibility, Voicebox compatibility, and the unified API are routed by hostname.

Open WebUI is the ordinary chat/RAG/voice surface. Its wrapper reads the generated internal service key from `/run/secrets/open_webui_api_key` and applies it to Open WebUI's OpenAI-compatible chat, RAG embedding, TTS, and STT settings, all pointing at the internal control-plane `/v1` API. Open WebUI global config persistence is disabled in this profile so migrated provider/search settings remain on disk but cannot override the LAN-only wrapper policy. Async image and video workflows are surfaced through Media Studio instead of Open WebUI's synchronous image plugin.

```text
LAN clients
  -> Caddy gateway
    -> Open WebUI
    -> Control Center
    -> Media Studio
    -> control-plane
      -> PostgreSQL
      -> Redis
      -> runtime-agent
      -> localai / comfyui / voicebox / audio-cpu
      -> artifact-server
```

The control plane owns model aliases, job state, scheduling, GPU leases, compatibility proxies, Model Hub metadata, Model Hub clients, Voicebox profile registry rows, runtime reservations, local browser users/sessions, API clients, and audit logs. PostgreSQL stores the durable scheduler owner/epoch and Redis stores the expiring live-owner key used during GPU execution. Redis renew and release operations compare the exact owner/epoch value atomically, and the long-lived GPU runner uses a per-instance owner string, so a restarted or duplicated control plane cannot refresh or delete a newer live lease with the same generic worker name. Redis is also used for pub/sub and queue coordination but is never the sole store of model, job, client, profile, reservation, or identity state.

Job records are exposed through two surfaces. Ordinary media-job routes are scoped to the authenticated owner for list, detail, cancellation, SSE events, and artifacts. Control Center uses `/admin/jobs`, limited to administrator/operator roles, for whole-queue filtering, inspection, priority changes, cancellation, and retry, with each mutation written to the audit log.

Runtime adapters define capability discovery, model-operation matching, health, native API compatibility flags, OpenAI-compatible HTTP capability, GPU requirement, and external-data status. `/admin/runtimes` exposes the versioned `b1-runtime-adapter/v1alpha1` contract for each adapter, including modalities, operations, the scheduler surface, submission/event surface, lifecycle hook surface, unload/recovery mechanism, metrics source, and whether external runtimes are intentionally excluded from runtime-agent control. The scheduler workstream builds on this resolver: public aliases are translated to immutable model versions and a selected adapter before work is persisted or submitted.

The first execution paths are intentionally lightweight. The control-plane CPU runner processes `audio-cpu` jobs from PostgreSQL, calls the internal CPU audio runtime for async TTS/STT jobs, stores returned speech or transcript artifacts, and recovers interrupted CPU work after restart without taking the GPU lease.

Installed chat, vision-language response, speech, and embedding aliases resolved to OpenAI-compatible runtimes such as `localai` are forwarded directly to the internal runtime. GPU-backed synchronous calls acquire the global scheduler-owner lease, run the same unload/VRAM/load/warm preparation path used by queued GPU jobs, then hold or renew the lease for the duration of the request or stream.

The GPU media runner processes `localai`, `comfyui`, and `voicebox` jobs through the same lease and records the required `waiting_for_gpu -> unloading -> verifying_vram -> loading -> warming -> running` path plus `started_at`, `load_time_ms`, `run_time_ms`, and peak runtime-agent VRAM/RAM samples where available. Database claims apply reservation filtering first, then the configured priority order with aging to prevent permanent starvation. When `b1_runtime_state` shows a GPU runtime idle with an immutable model version still resident, the claim selector may choose queued work for that same runtime/model ahead of a slightly older peer so compatible requests are grouped without another unload/load cycle. This grouping is bounded by the same aging score, so chat and other materially more urgent work still wins. The runner asks non-target GPU runtimes to unload through their `/b1/runtime/unload` hooks first, uses runtime-agent predefined unload/restart only when the graceful hook is unavailable or unconfirmed, verifies VRAM, then calls optional selected-runtime `/b1/runtime/load` and `/b1/runtime/warm` hooks before adapter submission. Scheduler-observed runtime states are persisted in `b1_runtime_state` and shown through the admin status/runtimes APIs. Cancellation is checked during long LocalAI and Voicebox runtime HTTP calls as well as between scheduler stages; a mid-call cancellation aborts the control-plane request, marks the job cancelled, and asks runtime-agent to recover the selected runtime before the lease is released. Prepared GPU runtimes are marked `idle` when queued or synchronous work finishes; when no GPU job is claimable, the runner applies the alias idle timeout or `B1_GPU_DEFAULT_IDLE_TIMEOUT_SECONDS`, acquires the same global lease, asks the runtime hook to unload the expired idle model, and falls back to runtime-agent unload/restart only when needed.

On control-plane startup, the control plane first reattaches trackers for native ComfyUI compatibility jobs that already persisted a native `prompt_id` and are still in `running`, `saving`, or `cancelling`. The CPU and GPU runners then record a bounded reconciliation result before claiming new work. `waiting_for_gpu` rows are requeued, while non-resumable jobs interrupted during unload, VRAM verification, load, warm, run, save, or cancellation are marked `recovery_required` for explicit operator retry. `GET /admin/scheduler/reconciliation` exposes both the native ComfyUI reattachment summary and runner startup records, including bounded sampled job IDs for requeued and recovery-required rows, for the live restart acceptance drill and final handoff report.

ComfyUI media jobs submit native prompt payloads or published workflow JSON to `/prompt`; published workflows can write validated form parameters into graph paths through `comfyui_parameter_mappings` before template substitution. The runner records the returned `native_prompt_id`, polls native history, ingests `/view` outputs into artifact-server storage, and then transitions through `saving -> completed`.

LocalAI image-generation jobs submit OpenAI-compatible JSON to `/v1/images/generations`; LocalAI image-edit jobs submit staged `image` and optional `mask` uploads to `/v1/images/edits`, with published workflows able to translate user-facing fields through `runtime_parameter_mappings`. LocalAI text-to-video jobs submit JSON to `/v1/videos/generations`, and image-to-video jobs submit a staged or data-URL image as multipart to `/v1/videos/image-to-video`. These LocalAI media paths persist returned `b64_json`, `b64`, `base64`, `data:` URL, or same-origin runtime URL media under artifact storage and fail to `recovery_required` if no media is returned.

Voicebox TTS jobs submit `/v1/audio/speech` under the GPU lease, store returned audio under artifact storage, and fail to `recovery_required` on empty output. Unsupported GPU runtime/job shapes fail with `failure_category=unsupported_gpu_operation` and no artifact, including non-speech Voicebox media jobs until their adapters mature.

Native ComfyUI compatibility `POST /prompt` traffic is also admitted through the same global lease and runtime preparation path, records admission and run timing, records the returned native `prompt_id`, marks ComfyUI idle after confirmed completion or cancellation, and holds/renews the lease in a background history tracker until ComfyUI records completion. Native ComfyUI `/ws` text and binary traffic is bridged through the control plane while preserving client ID query parameters; text events with prompt IDs update durable job progress and stream live output references into artifact storage before updating the durable job.

During `verifying_vram`, runtime-agent GPU metrics are used when available; above-reserve VRAM triggers a predefined runtime recovery action and a second verification before the job may continue. Runtime reservations are persisted as scheduler intent records and enforced for queued and synchronous GPU work by owner/runtime/immutable model version. The LocalAI production wrapper exposes scheduler hooks for pinned build identity, redacted one-backend guardrail status, model-list checks, optional tiny smoke/warm inference, and native backend shutdown. The ComfyUI production image exposes B1 hooks through a custom-node route package so native traffic remains unwrapped while scheduler preparation can observe model-folder checks, manifest-provided native prompt smoke, no-op fallback queue smoke, and native free-memory flags. The Voicebox production image exposes a B1 proxy that forwards native REST/web/WebSocket traffic to loopback upstream and adds conservative model-list, optional speech-probe, and idle upstream-restart lifecycle hooks. These production lifecycle hooks, plus the audio-cpu smoke hook, require the generated `runtime_control_token` bearer secret. Acceptance harnesses now require persisted model-smoke measurements for the selected immutable aliases before handoff evidence can go green; remaining target-host work includes collecting those RTX 3060 model/workflow measurements with real installed models and non-speech Voicebox media submission where upstream supports it.

Model Hub synchronisation is planned against catalog manifests before blob access. The public blob route only proxies content-addressed blobs that belong to downloadable catalog records, so inference-only and unknown blobs cannot be fetched through the Model Hub API even if a file exists in storage.

Installed model manifests are persisted in PostgreSQL and overlaid onto the seed catalog at control-plane startup. The authoritative blob store remains `$B1_DATA_ROOT/models/blobs`, mounted read-only only where blob distribution requires it. Inference runtimes mount `$B1_DATA_ROOT/models/runtime-views/{runtime}` read-only; after verifying blob size and SHA-256, the control plane creates per-model views there by hardlinking ordinary files and safely extracting supported archive-format blobs. Optional model smoke tests run through managed runtime hooks after installation, store bounded measurement history in the manifest, and conservatively update the resource estimate used by admission when measured RAM/VRAM peaks are higher. Quarantine moves those runtime views under `$B1_DATA_ROOT/models/quarantine/runtime-views` without deleting blobs.

Generated artifacts are also delivered through the control plane. Artifact URLs must be attached to durable job records before the control plane proxies them to the internal artifact-server. The control plane strips external credentials and injects the generated internal artifact-server bearer token, keeping ownership checks and API-key scope enforcement in the web-facing service while preserving range/resume support, SHA-256 entity tags, and checksum headers in the storage service.

Published workflows are persisted in PostgreSQL. Repository seed files are imported at startup from a read-only mount, then the API exposes role-filtered workflow discovery plus validation, publication, and unpublication endpoints. Dependency readiness is recorded with each workflow so uninstalled model aliases, missing runtimes, and unapproved ComfyUI custom-node pins are visible rather than failing at execution time. API responses derive an execution summary from that persisted state so operators and Media Studio can see candidate runtimes, ComfyUI requirement, GPU-lease need, queue class, and safe graph/input counts before submission. Workflow records include explicit modality, operation, model alias, runtime policy, backend policy, output MIME types, JSON Schema inputs, limits, and dependency metadata so Media Studio can submit durable jobs without hard-coded forms.

The runtime-agent is the only service intended to access the container runtime. It exposes a mutually authenticated TLS internal API plus a generated bearer token and must never provide arbitrary Docker passthrough. Bootstrap creates a private runtime-agent CA, server certificate, and control-plane client certificate under `$B1_DATA_ROOT/secrets`; the normal control-plane URL is `https://runtime-agent:8443`. Its Docker client filters containers by both Compose project and service labels, validates the labels returned by Docker before reporting or mutating a container, supports read-only status/log inspection, gates start/stop/restart behind `B1_ENABLE_MUTATIONS=false` by default, and restricts predefined runtime recover/unload actions to `B1_RUNTIME_ACTION_SERVICES`.

Runtime-agent metrics are similarly narrow: it reads fixed `/proc` host-memory/load data, configured B1 storage paths, Docker status, and optional `nvidia-smi` GPU telemetry. The web-facing control plane consumes those metrics through the mTLS/token-authenticated internal call for the admin self-test and dashboard surfaces.

The base repository slice uses placeholder internal runtimes for `localai`, `comfyui`, and `voicebox` so the topology can run without downloading model weights, while production overrides replace those services with pinned B1 runtime images for real GPU validation. The `audio-cpu` scaffold is also development-only and is policy-gated by `B1_CPU_AUDIO_ENABLE_PLACEHOLDER`; when disabled it reports `unconfigured` health, returns HTTP 503 from scaffold endpoints, and returns `status=unconfigured` from the smoke hook instead of producing placeholder output. Its authenticated lifecycle hooks report pinned Python/Piper build metadata, redacted model-probe booleans, no GPU lease requirement, CPU residency headroom, and `status=degraded` while any enabled operation still uses scaffold. Three real CPU paths now exist behind Model Hub installed runtime views: Piper TTS, ONNX Runtime embeddings, and Vosk STT. The default audio-cpu image installs checksum-pinned rhasspy/piper `2023.11.14-2`, and `B1_CPU_AUDIO_ENGINE=piper` runs that binary against the installed runtime view selected by the request's immutable model version. `B1_CPU_EMBEDDING_ENGINE=onnx` runs a pinned ONNX Runtime/tokenizer stack against the installed MiniLM runtime view and returns locally normalized embeddings without using the GPU or remote providers. `B1_CPU_STT_ENGINE=vosk` runs pinned Vosk Python bindings against an installed, safely extracted Vosk runtime view and transcribes bounded mono 16-bit PCM WAV input locally. The seed catalog includes available `b1-piper-en-us-amy-low`, `b1-minilm-l6-v2-onnx-q4`, and `b1-vosk-small-en-us-0.15` recommendations with exact file checksums; none becomes active for its alias until installed. The control plane treats remaining placeholder runtimes as a readiness policy, not a production claim: `B1_RUNTIME_DEPLOYMENT_MODE=development` reports placeholder required runtimes as a warning, while `production` fails self-test until `B1_RUNTIME_PRODUCTION_REQUIRED` runtimes are healthy and non-placeholder.
