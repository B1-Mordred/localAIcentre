# Backup and Restore

Backups must include:

- PostgreSQL dumps
- Open WebUI data
- Control Center settings, persisted runtime configuration, alias policy, and encrypted-secret metadata
- model manifests and custom or non-redownloadable weights
- workflows and approved node pins
- Voicebox profiles and reference samples
- selected artifacts
- Caddy PKI and generated secrets required for continuity

Use:

```bash
make backup
```

The backup command creates `$B1_DATA_ROOT/backups/<timestamp>/manifest.json` and `payload.tar.gz`. When backup encryption is enabled, it also writes `payload.tar.gz.aesgcm`; in `encrypted-only` mode the plaintext payload is removed after the encrypted archive is verified. The manifest records the plaintext archive checksum, encrypted archive checksum when present, file-level SHA-256 checksums, included paths, excluded paths, and whether sensitive data such as secrets or Caddy PKI is present.

`make backup` loads `.env` when present, writes to `B1_BACKUP_ROOT`, and passes `B1_BACKUP_ENCRYPTION_KEY_FILE`, which defaults to `$B1_DATA_ROOT/secrets/master_encryption_key`. This keeps the host-side wrapper aligned with the Control Center backup format. The web-managed backup path remains preferred for production because it also creates fresh logical and native PostgreSQL dumps before archiving.

The same operation is available from Control Center Storage and from the admin API:

```bash
curl -X POST https://api.ai.b1.germering/admin/backups \
  -H "Authorization: Bearer $B1_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{}'
```

The control-plane backup API is constrained to `$B1_DATA_ROOT`, writes only to `$B1_BACKUP_ROOT`, and does not accept arbitrary host paths. Before building the archive it writes both `data/control-plane/postgres-logical-export.json` and `data/control-plane/postgres-native.dump`, then marks PostgreSQL coverage in the manifest with `postgres_dump_included=true`, `postgres_dump`, `postgres_dumps[]`, and `postgres_native_dump`. The logical export includes local user accounts, password hashes, Voicebox profile registry rows, API clients, encrypted-secret metadata/envelopes, persisted external-runtime configuration, model alias policy rows, model-download records, persisted resource-policy override, maintenance-mode state, controlled update rows, model records, workflows, jobs, and audit events so administrators remain recoverable; active browser sessions are not exported and users sign in again after restore. The native dump is a `pg_dump --format=custom --no-owner --no-privileges` file generated by the control-plane image with credentials passed through libpq environment variables, not shell command strings. Voice reference sample bytes are included only through the normal Voicebox data/artifact filesystem backup paths, not inline inside profile rows.

`B1_BACKUP_ENCRYPTION_MODE` controls archive encryption for web-managed backups. `copy` is the default: the control plane keeps the local `payload.tar.gz` for normal restore tests and writes an encrypted `payload.tar.gz.aesgcm` for off-host storage. `encrypted-only` removes the plaintext archive and requires the same master encryption key to verify or restore. `none` disables encrypted archive generation. Encryption uses chunked AES-GCM with the key derived from `$B1_DATA_ROOT/secrets/master_encryption_key`; keep that key in a separately protected disaster-recovery location because an encrypted-only backup cannot decrypt itself.

Default filesystem backup includes:

- Open WebUI data
- control-plane data
- Voicebox data
- Caddy data/PKI
- model directories except reproducible blobs and runtime views
- recoverable blob quarantine staging under `models/quarantine/blobs`
- workflows
- selected artifacts
- generated secrets
- control-plane and runtime-agent logs

Encrypted-secret rows are usable after restore only when the same `$B1_DATA_ROOT/secrets/master_encryption_key` is restored. Without that generated key file the metadata remains visible, but verify/decrypt operations fail and dependent providers or integrations must be re-entered.

Default exclusions avoid backing up reproducibly downloadable blobs, caches, previous backups, and live PostgreSQL/Redis data directories:

- `models/blobs`
- `models/runtime-views`
- `models/quarantine/runtime-views`
- `cache`
- `backups`
- `restore-tests`
- `data/postgres`
- `data/redis`

Active reproducibly downloadable blobs are excluded by default because they can be re-synchronized through Model Hub. Blobs that an operator explicitly moved to `models/quarantine/blobs` are included by default so cleanup remains recoverable until the operator applies model quarantine retention cleanup from the Storage tab or `/admin/models/quarantine/cleanup`.

Backup retention is dry-run first. The Control Center Storage tab and API can plan cleanup with a `keep_last` count and optional `delete_older_than_days` threshold. The newest `keep_last` backups are always preserved. If an age threshold is set, backups outside the newest set are candidates only when their manifest `created_at` is older than the threshold. Invalid backup directories and symlinked entries are reported but preserved.

```bash
curl -X POST https://api.ai.b1.germering/admin/backups/retention-plan \
  -H "Authorization: Bearer $B1_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"keep_last": 5, "delete_older_than_days": 30}'
```

Applying cleanup requires `storage:write` and `confirm=true`. The control plane re-runs the retention plan immediately before deletion and removes only validated direct child backup directories under `$B1_BACKUP_ROOT`. It refuses symlinked backup directories and backup directories containing symlinked content.

```bash
curl -X POST https://api.ai.b1.germering/admin/backups/cleanup \
  -H "Authorization: Bearer $B1_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"keep_last": 5, "delete_older_than_days": 30, "confirm": true}'
```

Model blob quarantine retention is also dry-run first. `POST /admin/models/quarantine/retention-plan` scans only `$B1_DATA_ROOT/models/quarantine/blobs`, reports old recoverable quarantine batches, and preserves malformed or symlinked entries. Applying `POST /admin/models/quarantine/cleanup` with `confirm=true` deletes only validated old quarantine batch directories; it never deletes active authoritative blobs or runtime views.

```bash
curl -X POST https://api.ai.b1.germering/admin/models/quarantine/retention-plan \
  -H "Authorization: Bearer $B1_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"delete_older_than_days": 30, "limit": 5000}'
```

## Scheduled Backups

Scheduled backups are disabled until an administrator enables the stored policy from Control Center Storage or `PUT /admin/backups/schedule`. The policy records:

- enabled/disabled state
- interval in hours
- backups to keep
- optional age threshold for cleanup
- safe backup label prefix
- next run, last run status, last backup name, and failure message

The background scheduler runs inside the control plane when `B1_BACKUP_SCHEDULER_ENABLED=true`. It polls at `B1_BACKUP_SCHEDULER_INTERVAL_SECONDS`, atomically claims a due schedule row, creates the same constrained backup as the manual API, applies the stored retention policy, advances `next_run_at`, and audits success or failure as `system:backup-scheduler`. It never accepts arbitrary paths, include lists, or shell commands from the schedule row.

The Storage tab's Run button executes the stored schedule policy immediately. It is useful for testing retention behaviour before waiting for the next scheduled time.

Restore only into an alternate directory:

```bash
make restore BACKUP=/srv/b1-ai-hub/backups/20260722-120000 RESTORE_ROOT=/srv/b1-ai-hub-restore-test
```

Restore verifies the archive checksum and every restored file checksum, writes `restore-report.json`, and refuses to extract into a non-empty target unless `deploy/scripts/restore.py --force` is used for a controlled alternate-directory test. If `payload.tar.gz` is absent and `archive_encryption` is present, restore decrypts `payload.tar.gz.aesgcm` through a temporary file, verifies the plaintext checksum from the manifest, and then extracts. Restore extraction writes regular files explicitly instead of using tar `extractall`, rejects absolute paths, traversal, Windows drive paths, unmanifested files, duplicate file entries, symlinks, hardlinks, device nodes, and pre-existing symlinked destination paths, then normalizes restored file permissions. When a native PostgreSQL dump is present, restore-test also runs `pg_restore --list` against the extracted custom-format dump and records `postgres_native_dump_verification`.

For an encrypted-only off-host restore, provide the restored master key file explicitly:

```bash
python3 deploy/scripts/restore.py \
  --backup /srv/b1-ai-hub/backups/20260722-120000 \
  --target /srv/b1-ai-hub-restore-test \
  --backup-encryption-key-file /secure/offhost/master_encryption_key
```

The Control Center/API restore test is similarly constrained. It restores only to `$B1_RESTORE_TEST_ROOT/<backup-name>`:

```bash
curl -X POST https://api.ai.b1.germering/admin/backups/20260722-120000/restore-test \
  -H "Authorization: Bearer $B1_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"force": false}'
```

Verification without extraction is available at:

```bash
curl -X POST https://api.ai.b1.germering/admin/backups/20260722-120000/verify \
  -H "Authorization: Bearer $B1_ADMIN_KEY"
```

After a restore test has extracted the archive, the API can validate the PostgreSQL logical export and return a dry-run import plan:

```bash
curl -X POST https://api.ai.b1.germering/admin/backups/20260722-120000/postgres-import \
  -H "Authorization: Bearer $B1_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"apply": false}'
```

Applying the logical import upserts the exported rows into the current control-plane database. Run migrations first so the target schema is current, then apply the import. The import is intentionally gated by an explicit backup-name confirmation:

```bash
make db-migrate
```

```bash
curl -X POST https://api.ai.b1.germering/admin/backups/20260722-120000/postgres-import \
  -H "Authorization: Bearer $B1_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"apply": true, "confirm_backup_name": "20260722-120000"}'
```

The host CLI can also mark a pre-created database dump in the manifest:

```bash
python3 deploy/scripts/backup.py \
  --root /srv/b1-ai-hub \
  --postgres-dump-file /srv/b1-ai-hub/data/control-plane/postgres-logical-export.json \
  --postgres-dump-format b1-ai-hub-postgres-logical-export/v1 \
  --postgres-native-dump-file /srv/b1-ai-hub/data/control-plane/postgres-native.dump \
  --backup-encryption-mode copy \
  --backup-encryption-key-file /srv/b1-ai-hub/secrets/master_encryption_key
```

Native dump coverage is now part of every control-plane backup when the PostgreSQL client tools are present in the image. The web-managed PostgreSQL import endpoint still uses the B1 logical JSON upsert path because it is non-destructive against an already running control-plane database. Full native `pg_restore` apply remains an offline disaster-recovery operation for an empty replacement database and must be run only after the backup archive and `pg_restore --list` verification pass. Encrypted off-host handling is implemented for the archive payload; operators must still keep the decryption key separately protected and test restore before relying on off-host copies.

## Old-Stack Migration Backups

The normal `make backup` command protects B1 AI Hub state. It does not automatically capture the deployment that B1 AI Hub is replacing.

For the old stack, first create a read-only inventory, then generate an operator scope template:

```bash
make inventory
make old-stack-scope INVENTORY=/srv/b1-ai-hub/backups/inventory-20260722-120000.json
```

The generated scope selects no resources by default. It carries the inventory's port-review, model-storage, and Open WebUI SQLite metadata summaries so operators can review old-stack evidence without reading prompts, chats, `.env` files, or database row contents. After reviewing the inventory, set `operator_reviewed=true`, fill `reviewed_by`, and add only confirmed old AI stack paths, Docker volumes, and container names. Unknown services and explicitly unrelated services remain out of scope.

Then create and verify the old-stack backup:

```bash
make old-stack-backup SCOPE=/srv/b1-ai-hub/backups/old-stack-scope.json
make old-stack-backup-verify BACKUP=/srv/b1-ai-hub/backups/old-stack-20260722-120000
```

The old-stack archive is read-only evidence for migration and rollback. Its manifest sets `old_stack_deletion_allowed=false`; successful backup verification is not permission to remove old volumes, model files, databases, Compose files, or configuration.

After verification, generate the Open WebUI preservation plan:

```bash
make open-webui-migration-plan \
  INVENTORY=/srv/b1-ai-hub/backups/inventory-20260722-120000.json \
  BACKUP=/srv/b1-ai-hub/backups/old-stack-20260722-120000
```

The plan verifies the old-stack backup again, matches inventoried Open WebUI database candidates to manifest entries, records Open WebUI container image/tag evidence from the inventory, and warns when a readable database is not actually preserved by the backup. It also warns when source-version evidence is missing or the old Open WebUI image used a floating tag. It does not read row contents, import data automatically, or approve direct database reuse; operators restore to an alternate directory and test a supported Open WebUI migration/export/import path before cutover.

Once the backup verifies, generate the reviewed cutover/rollback runbook:

```bash
make cutover-plan \
  INVENTORY=/srv/b1-ai-hub/backups/inventory-20260722-120000.json \
  SCOPE=/srv/b1-ai-hub/backups/old-stack-scope.json \
  BACKUP=/srv/b1-ai-hub/backups/old-stack-20260722-120000 \
  OPEN_WEBUI_PLAN=/srv/b1-ai-hub/backups/open-webui-migration-plan.json
```

The cutover planner verifies the backup again, refuses resources classified as unrelated or current B1 AI Hub, refuses occupied temporary staging ports, validates the Open WebUI preservation plan input, and writes only a non-destructive plan. Existing production or optional legacy ComfyUI listeners are reported in `port_readiness`; intended virtual-host DNS records are reported in `dns_readiness`; Open WebUI preservation evidence is reported in `open_webui_preservation`, including the source-version compatibility status. Missing or divergent DNS records and unresolved Open WebUI preservation warnings become warnings for operator review. The planner never stops containers, rewrites DNS, deletes files, imports Open WebUI data, or marks the old stack removable.
